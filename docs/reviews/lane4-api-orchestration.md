## Findings

1. **`queue` top-level response hardcodes `speed`/`kbpersec` to "0" despite computing the real value** — `internal/api/queue.go:418-421` computes `speed := s.status.Speed()` and uses it correctly for each slot's per-job ETA (`buildSlot`, line 297+), but the queue-level `queueDetail.Speed`/`KBPerSec` fields are literal string constants `"0"` (lines 476-478), never populated from `speed`. CONFIRMED, traced end-to-end. Lens: wire-contract fidelity (stub-that-lies). Third-party dashboards (NZB360-style) that read the top-level speed field see permanent 0 even while actively downloading. Effort: S (one-line fix using `humanfmt`/existing `speed` var, same pattern as the per-slot code just above it).

2. **`change_complete_action` is a pure no-op that returns success** — `internal/api/queue.go:93-95`: `func (s *Server) queueChangeCompleteAction(w http.ResponseWriter, _ *http.Request) { respondStatus(w) }`. No config value is read, stored, or applied anywhere in the codebase (grepped `change_complete_action`, `finishaction`). A client setting "shutdown PC when queue finishes" gets `{"status":true}` and believes it worked. CONFIRMED. Lens: wire-contract fidelity — this is the single clearest "stub that lies" in the surface. Effort: S to make it return an explicit not-implemented error instead (matching the `queueNotImplemented` pattern used two lines above it for `sort`/`delete_nzf`); L to actually implement the behavior.

3. **`config&name=set_apikey`/`set_nzbkey` are absent, with a code comment that misstates the spec** — `internal/api/config.go:288-290` rejects both with "unknown config action" and the comment `// Not in spec for get_config/set_config modes`. The spec (`docs/sabnzbd_spec.md:894-895`) explicitly lists both under `mode=config`. CONFIRMED (grep shows no other implementation of key regeneration exists). Lens: wire-contract fidelity + comment accuracy. A caller wanting to rotate a leaked key via the API cannot; they must edit the YAML file directly and restart, or use `set_config` to push an arbitrary (not server-random) value. Effort: M (needs `newAPIKey()` from `internal/config/defaults.go` exposed, config persistence, and a response shape).

4. **`queue` response omits most of the spec's documented top-level fields** — `diskspace1/2`, `diskspacetotal1/2`, `quota`/`have_quota`/`left_quota`, `cache_art`/`cache_size`/`cache_max`, `speedlimit`/`speedlimit_abs`, `pause_int`, `paused_all`, `version`, `loadavg`, `finishaction` are all present in the spec's example (`docs/sabnzbd_spec.md:916-977`) but absent from `queueDetail`/`queueResponse` (`internal/api/queue.go:170-192`). CONFIRMED. Some of these genuinely don't apply to gonzbd (no bandwidth quota feature exists), but disk space is a real, implemented feature (`StatusReporter.DownloadDirFreeBytes` exists and is used elsewhere, e.g. `status_overview`) that simply isn't surfaced on the `queue` endpoint third-party clients actually poll. Lens: wire-contract fidelity. Effort: M.

5. **`queue`/`history` slot objects omit several spec fields** (`avg_age`, `has_rating`, `mbmissing`, `unpackopts`, `labels` on queue slots) — `internal/api/queue.go:104-157`. Not lying (fields are simply absent, JSON marshaling just won't include them), but any client parsing struct-typed responses (rather than dynamic maps) that expects these keys will silently get zero values. CONFIRMED. Lens: wire-contract fidelity. Effort: S–M depending on field (labels/has_rating are trivial stub values; avg_age/mbmissing require real computation).

6. **Several documented top-level modes are entirely unregistered** (`switch`, `get_files`, `move_nzf_bulk`, `retry`, `retry_all`, `cancel_pp`, `showlog`, `gc_stats`, `reset_quota`, `restart_repair`, `test_email`, `test_notif`, `set_config_default`, `eval_sort`) — confirmed absent from `modeTable` in `internal/api/router.go:77-124` via grep across `internal/api/*.go`. These fail with an honest 400 "unknown mode: X" rather than lying, which is the good version of a coverage gap, but `retry`/`cancel_pp`/`switch` are plausible things a media manager might call for job-management workflows and their absence is a real capability gap, not merely a niche one. `eval_sort` is explicitly and correctly marked NOT IMPLEMENTED in the spec itself (sorting is out of scope by design), so that one is not a gap. Lens: wire-contract coverage. Effort: varies (S per mode to add a 501 stub for honesty; M–L to implement each for real).

7. **`isStateChangingMode`/CSRF classification references modes not present in the router** — `internal/api/helpers.go:134-142` (`isSystemMutationMode`) is fine (only lists implemented modes), but `helpers_test.go:145-146` tests `"switch"` as a state-changing name even though `mode=switch` doesn't exist in `registerModes`. This is dead/aspirational test coverage rather than a functional bug (the classification function only matters for modes that are actually routable), but it's a latent inconsistency: if `switch` is ever added as a top-level mode it needs its own `isStateChangingMode` branch (currently falls through the `default: return false` in `isStateChangingMode`, which would make a POST-required mutation reachable via unauthenticated cookie-GET). INFERRED (no such mode exists today so it's not exploitable yet, but the fail-open default is worth flagging pre-emptively). Lens: security surface. Effort: S (note in a comment or add to the switch when the mode is implemented).

8. **`output=xml` variant documented in the spec is not implemented anywhere** — grepped `internal/api` for `xml`/`output` handling; none found. All responses are JSON regardless of `output=` query param. INFERRED absence (didn't find a counter-example, but the search was thorough: no `encoding/xml` import anywhere in `internal/api`). Lens: wire-contract fidelity. Some SABnzbd-API clients (older scripts) request `output=xml`; they would get JSON back with a 200, which the client may mis-parse. Effort: L if genuinely needed (full XML marshaling for every response type); worth checking whether any real client actually needs it before investing.

9. **`fullstatus` is a thin subset of the documented "All queue, server, stats" response** — `internal/api/status.go:9-33` returns only `paused`, `noofslots`, `last_warning`, `completedir`. This mode is explicitly called out in `router.go:70-76` as SABnzbd-compat-only (not used by the bundled UI), so any regression here is invisible to first-party testing and would only be caught by a third-party client integration test. INFERRED (spec text is not a strict schema for this endpoint, but the gap between "all queue, server, stats" and four fields is large). Lens: wire-contract fidelity. Effort: M.

10. **Shutdown ordering matches the documented required order exactly** — `internal/app/app.go:715-799` (`Shutdown`) and `stopWorkers` (`729-760`) implement, in order: (1) stop downloader, (2) abort DirectUnpackers, (3) stop assembler, (4) cancel context, (5) `wg.Wait()`, (6) stop post-processor, (7) save queue. This is a precise match to `docs/go-standards.md` §3's "stop producers → drain consumers → cancel context → wait → cleanup" and to `docs/ARCHITECTURE.md`'s Startup Sequence step 10. CONFIRMED, and the code comments explicitly cross-reference the ordering rationale (`app.go:715-728`). Lens: concurrency/persistence. This is a **positive** finding — see Positive section.

11. **Every shutdown step is individually time-bounded via `waitBounded`** — `internal/app/app.go:693-713`, used for downloader stop, assembler stop, `wg.Wait()`, and post-processor stop (each wrapped independently in `Shutdown`/`stopWorkers`). A wedged goroutine in one subsystem can't hang the whole daemon shutdown indefinitely; it logs "shutdown step exceeded budget; abandoning" and moves on. CONFIRMED. Lens: concurrency. Positive finding, but note it also means a genuinely stuck downloader will be silently abandoned rather than the process refusing to exit — acceptable tradeoff for a daemon, flagged for awareness not as a defect.

12. **`Start()`'s failure-path cleanup correctly cancels the context it created**, even though `app.started` is reset to `false` — `internal/app/app.go:582-608`. The deferred cleanup is careful to distinguish "succeeded" from a failure that leaves 4 long-lived goroutines needing a cancel signal nobody else will send (comment explicitly walks through why `Shutdown()` can't be relied on here, since its own started-guard would short-circuit). CONFIRMED by reading the logic; this is subtle and well-reasoned. Lens: concurrency. Positive.

13. **`ReloadDownloader` lock discipline is unusually well-documented and defensible** — `internal/app/reloader.go:126-184`. Uses a dedicated `reloadMu` (separate from `app.mu`) to serialize the whole reload end-to-end while `app.mu` is only held for the brief pointer-swap moments, explicitly to avoid holding a mutex across `Stop()`/`Start()` I/O (go-standards.md §1's "never hold a mutex during disk I/O or network calls" rule). The comment at lines 129-141 walks through exactly why two concurrent reloads would otherwise interleave badly. CONFIRMED. Lens: concurrency. Positive — this is exactly the kind of documented lock-choice the project's own conventions ask for.

14. **`stopWorkers` takes `reloadMu` before snapshotting `app.downloader`, specifically to wait out an in-flight `ReloadDownloader`** — `internal/app/app.go:738-742`, with an explicit comment explaining the race it closes (a reload that swaps in a new downloader after `stopWorkers` already captured the old one, leaving the new one never stopped). CONFIRMED by reading the code and cross-referencing `reloader.go`. Lens: concurrency. Positive — non-obvious cross-file interaction that's actually been thought through and documented, not just accidentally correct.

15. **`main.go` is 1169 lines and does more than pure wiring** — beyond flag parsing and orchestration, it implements CSP header construction (`contentSecurityPolicy`, lines 728-749), a full second request-logging middleware (`requestLoggingMiddleware`, `routerStatusWriter`, lines 656-713, largely duplicating `internal/api`'s `statusWriter`/`loggingMiddleware`), a security-headers handler, and a `trustGate` implementation. None of this is business logic and each piece is well-commented, but it means `internal/web` or a new small `internal/httpserver`-style package could absorb the HTTP-plumbing pieces (CSP, security headers, the duplicate status-capturing writer) rather than `cmd/gonzbd`. INFERRED as a structural observation, not a correctness bug — the code is correct and tested (`router_test.go`, `https_test.go`). Lens: idiom/quality. Effort: M if pursued, and not obviously worth it given how small each individual test-covered piece is.

16. **Duplicate `statusWriter`/status-capturing-ResponseWriter implementation** between `internal/api/middleware.go` (`statusWriter`, lines 449-478, with `Hijack()` for WebSocket passthrough) and `cmd/gonzbd/main.go` (`routerStatusWriter`, lines 662-681, without `Hijack()`). The main.go comment explicitly justifies the duplication ("kept separate since it's a different package with no shared logging abstraction... doesn't need the Hijacker passthrough"). CONFIRMED duplication exists; the stated rationale is reasonable but this is exactly the kind of two-line type that could live in a tiny shared package (e.g. `internal/httputil`) if a third consumer ever appears. Lens: idiom/quality. Effort: S if ever consolidated; not urgent.

17. **`app.Application` genuinely does own a very large surface, but the bulk of it is thin pass-through/reload glue, not tangled business logic** — of `app.go`'s 1487 lines, a large fraction is: (a) `New()` construction wiring (~200 lines), (b) `Start`/`Shutdown`/lifecycle (~230 lines, heavily comment-documented), (c) single-purpose `SetX`/`ReloadX` pass-throughs to the downloader/queue/config (dozens of 3-10 line methods), (d) the on-demand-PAR2 decision logic (`maybeReleaseRecoveryVolumes`/`par2NeedsRecovery`, ~110 lines) which is genuine domain logic that arguably belongs to `queue` or a dedicated `par2` orchestration type rather than `app` itself. See "internal/app assessment" below for the full verdict.

18. **`modeHealth`'s JSON field type for `status` differs by auth level** — unauthenticated: `{"status": "ok"}` (string); authenticated: `{"status": true}` (bool) — `internal/api/health.go:69-79`. `mode=health` is a gonzbd-only extension (not in the SABnzbd spec's mode table), so this isn't a wire-contract violation for third-party SABnzbd clients, but it is an internal inconsistency a bespoke health-check consumer (e.g. a Docker HEALTHCHECK script or k8s probe parsing this JSON) could trip on if it expects a stable type. INFERRED as a real but low-severity type wart. Lens: idiom/quality. Effort: S (return `false`/`true` consistently, or restructure to avoid the shared field name).

19. **`percentage` field type test is a strong positive practice** — `TestQueueSlot_SonarrPercentageIsInt` (`internal/api/queue_test.go:1342-1365`) is exactly the kind of adversarial-consumer-shaped regression test the task brief calls out as the classic SABnzbd number-vs-string trap, and it's present and passing. This suggests the team is already alert to this class of bug elsewhere (see also `TestQueueSlot_SonarrIndexField` immediately following it). Positive finding — flagging so synthesis credits it rather than only surfacing gaps.

20. **`formValue`'s body-vs-query precedence is the opposite of `apiKeyFromRequest`'s, and this asymmetry is deliberate and documented** — `helpers.go:36-56` (`formValue`): POST body **takes precedence over** query string for ordinary parameters. `roles.go:123-160` (`apiKeyFromRequest`): query string is checked **before** the POST body, specifically for `mode`/`apikey`/`nzbkey` per the go-standards.md §4 rule. Both are internally consistent with their stated purposes (auth/routing needs to resolve before any body parsing is safe; ordinary params can prefer the more specific POST value), but a future maintainer skimming `formValue` and assuming it governs auth-param resolution too would introduce a bug. CONFIRMED intentional (comments on both functions explain the difference) — flagging as a documentation/discoverability risk, not a current bug. Lens: idiom/quality. Effort: S (a one-line cross-reference comment in each function pointing at the other).

21. **`modeAddURL`'s doc comment flags a known behavioral gap (blocking fetch) but it's accepted as low-risk** — `internal/api/queue.go:811-818`: Python's `addurl` returns immediately (async fetch); gonzbd's blocks the HTTP response until the remote NZB is fully fetched. The comment says "Revisit if it hurts in practice." For a large/slow remote NZB source, this could tie up the client's HTTP timeout (Sonarr/Radarr have their own request timeouts and may treat a slow addurl as a failure, retrying and creating duplicate-detection load). INFERRED risk (no evidence of it actually causing problems, and duplicate detection in `AddJob`/`detectDuplicateNZB` would catch a retried duplicate). Lens: wire-contract behavior (timing behavior can matter for API contracts even when not called out in spec's schema). Effort: M if made async (needs a `nzo_id` pre-allocation + background fetch design).

22. **`app.Application.Speed()`, `ServerStatus()`, `UnblockServer()`, etc. all take `app.mu` around a read of `app.downloader`/`app.downloaderStats` and never hold it during the actual downloader call** — e.g. `Speed()` (`app.go:365-372`) holds `app.mu` for the entire `app.downloaderStats.Speed()` call, whereas `UnblockServer` (`app.go:1380-1387`) does the same but for a call that could plausibly do more work. These are all fast, non-blocking calls in the current implementation (no I/O), so this doesn't violate go-standards.md §1's "never hold a mutex during disk I/O or network calls" rule today, but the pattern is inconsistent with the "snapshot-then-release" pattern used everywhere else in the file (`handleLowDisk`, `PauseDownloads`'s sibling `pushDispatchOptions`, `RemoveJob`'s DisconnectAll check) — those use `app.mu.Lock(); dl := app.downloader; app.mu.Unlock()` explicitly to avoid holding the lock across the downstream call. If any of `Speed()`/`ServerStatus()`/`UnblockServer()` ever start doing anything even slightly more expensive on the downloader side, they'd silently violate the project's own documented pattern without a code reviewer necessarily noticing, because the surrounding file trains reviewers to expect the snapshot-release idiom. INFERRED (not a bug today — confirmed by reading `downloader.Speed()`/`ServerStatus()`/`UnblockServer()` call shapes are cheap in-memory reads) but worth flagging as an inconsistency. Lens: concurrency. Effort: S (mechanical snapshot-then-release conversion for consistency).

## internal/app assessment

**Verdict: legitimate integration point that has accreted some domain logic it could shed, not a runaway god object.**

Evidence for "legitimate integration point":
- The package's own doc comment (`app.go:1-5`) accurately states its job: wire queue → downloader → decoder → assembler, own subsystem lifecycles, bridge via the pipeline goroutine. Reading the file top to bottom, that's what it actually does.
- Construction (`New`, lines 149-346) is almost entirely dependency wiring: build the queue, probe sparse-file support, construct the downloader, apply bandwidth config, build the pipeline, probe binaries and build postproc stages, wire the assembler's callbacks. This is inherent integration-point work — there's no obvious "extract this into its own package" seam because each piece genuinely needs references to 3-4 sibling subsystems to wire together.
- The `Set*`/`Reload*` methods (`reloader.go`, and `app.go`'s `SetSpeedLimit`/`SetBandwidthMax`/`SetDownloadDir`/etc.) are almost all 3-10 line pass-throughs to a single subsystem, guarded by `app.mu`. This inflates line count without inflating complexity — it's necessary surface area for the API layer's `DownloaderControl`/`ConfigReloader` role interfaces (`internal/api/roles.go`) to have something to call.
- The shutdown/lifecycle code (items 10-14 above) shows real, hard-won concurrency correctness reasoning specific to *this* integration point (reload racing shutdown, reload racing itself, Start's failure path). That's exactly the kind of logic that has to live at the point where multiple subsystems' lifecycles meet — it can't be pushed down into any single subsystem.
- Its bug-magnet status per the repo's own churn data ("70 bug fixes, last fix yesterday") is consistent with "this is where every cross-subsystem interaction bug surfaces" rather than "this file is badly designed" — an integration point is definitionally where N subsystems' edge cases collide, so it will always have disproportionate bug-fix churn relative to any single subsystem, independent of code quality.

Evidence the package carries some logic that could be pushed out:
- `maybeReleaseRecoveryVolumes`/`par2NeedsRecovery` (app.go:865-972, ~110 lines) is genuine PAR2-repair-decision domain logic — parsing PAR2 index files, comparing CRC sets, classifying corruption reasons — not integration glue. It reads more naturally as part of `internal/par2` or `internal/queue` (it already imports `par2` and operates purely on `queue.Manifest`/`queue.JobProgress` plus a directory path — no `Application` state is used inside `par2NeedsRecovery` itself, which is already a free function, not a method). `maybeReleaseRecoveryVolumes` (the method) is a thin orchestration wrapper around it and could stay in `app`.
- `detectDuplicateNZB` (app.go:374-411) mixes three different duplicate-detection strategies (in-memory queue, history DB search, filesystem stat of the nzb backup dir) inline in one function. This is reasonable per-lens (all three need `Application`-level references), but it's a candidate for the "Simplify Multi-Strategy Fallbacks" pattern from go-standards.md §6 if it grows further.
- `failMsgForJob` (app.go:1419-1456) is a free function (not a method) with no `Application` dependency — it's already correctly *not* coupled to the struct, a good sign that extraction discipline exists in the codebase, but it sits in `app.go` rather than `queue` where its only inputs (`*queue.Job`) live.

Overall: the package is doing the job its own doc comment claims, at roughly the size that job requires. The par2-decision logic is the one piece that reads as misplaced domain logic rather than orchestration; everything else that inflates the line count is either necessary wiring or well-justified concurrency-correctness code specific to being the integration point.

## Security surface, right-sized

Per the brief: single-user, reverse-proxy-fronted, API key doubles as the third-party-client credential.

**Defensible (real threat model, keep as-is):**
- **CSRF protection (Origin + Sec-Fetch-Site + Referer fallback chain, `roles.go:263-315`)** — this protects the browser-facing session-cookie path specifically. A logged-in browser with the `gonzbd_apikey` cookie is a real CSRF target regardless of single-user-ness: any malicious site the operator's browser visits could otherwise fire mutating requests using the ambient cookie. This is correctly scoped to the cookie path only (`callerLevel`, `roles.go:79-84`) — API-key/NZB-key callers (Sonarr etc.) never hit this check. **Keep.**
- **Cookie-to-trusted-source binding (`IsTrustedRemote` check on the cookie path, `roles.go:85-104`)** — closes the documented SEC-1 attack (steal cookie via `GET /`, replay from elsewhere). Since the cookie is a full-admin credential and the proxy sits in front, this is exactly the right layer to enforce "who gets handed the cookie in the first place" — it's not redundant with proxy auth because the proxy doesn't know about this app-level session concept. **Keep.**
- **Separate ephemeral `SessionKey` vs. permanent `APIKey`** (`roles.go:44-50`) — a leaked browser cookie can't be replayed as the permanent third-party-integration credential, and it self-invalidates on restart. This is proportionate defense-in-depth for a browser-facing surface, not RBAC ceremony. **Keep.**
- **API-key vs NZB-key tiering (Protected vs Admin)** — this is NOT multi-user RBAC; it's a scoped-credential pattern (upload-only key vs full-control key) that SABnzbd itself has for good reason: an automation tool (Sonarr) only needs upload/queue access, and handing it the full admin key needlessly widens blast radius if that credential leaks from Sonarr's own config. **Keep**, and it's explicitly *not* removable per the brief since third-party clients depend on it.
- **`mode=auth` being LevelOpen** (`router.go:80-89`) — the code's own comment already does the honest cost/benefit analysis (constant-time compare + 64-bit keyspace makes brute force impractical; required for SABnzbd client-compat key classification) and tracks it as an accepted-risk issue (#112). This is correctly reasoned, not blind spec-compliance. **Keep as documented.**
- **`/debug/` trust-gating (`trustGate`, main.go:715-726)** — expvar leaks `os.Args`/memstats; gating it to loopback/local-ranges (the same predicate as the session cookie) rather than leaving it wide open is proportionate, cheap, and doesn't get in the way of the legitimate single operator. **Keep.**
- **`modeHealth`'s auth-tiered response detail** (`health.go:66-85`) — leaking DB/disk/pipeline diagnostic detail only to authenticated callers, while still giving unauthenticated load-balancer-style health checks a bare ok/error, is a good proportionate design: it doesn't force every health-check caller to carry a credential, but it also doesn't hand a pipeline-stall/low-disk-space signal to any unauthenticated network caller. **Keep.**

**Arguably ceremony for this threat model (worth questioning, not necessarily removing):**
- **`Sec-Fetch-Site` + `Referer` + `Origin` three-way fallback chain in `isCrossOrigin`** (`roles.go:282-315`) is more layered than most single-user self-hosted tools bother with. It's not wrong, and the code is clean (each check extracted to its own testable helper per go-standards.md §6's guidance), but for a reverse-proxy-fronted, single-operator daemon, the marginal value of the third fallback layer (Sec-Fetch-Site, a very recent browser feature with good default coverage already from Origin) versus its complexity/test-surface cost is genuinely debatable. Not flagging as "remove it" — the browser-CSRF threat is real per above — just noting it's the most elaborate piece of ceremony in the file relative to the population of users (one) it protects.
- **Constant-time comparison on `mode=auth`'s three-way key check** (`router.go:143-152`) is correct practice, but combined with the 64-bit keyspace argument already made in the code comment, the actual marginal protection from constant-time comparison specifically (as opposed to just rate-limiting, which doesn't exist) is small. This is cheap to keep (no real cost) so there's no argument for removing it — flagging only because the code's own comment already does more risk analysis than the mechanism strictly needs.
- **`isStateChangingMode`'s fail-closed design for `queue`/`history` sub-actions** (`helpers.go:144-173`) is good engineering (documented rationale: enumerating mutations previously missed some), but it exists entirely to gate the *cookie* auth path's CSRF POST-only rule — for the API-key path (the only path third-party clients use) none of this matters. This is correctly scoped already (it's not applied to API-key callers), so it's not ceremony, just noting the boundary is worth remembering when adding new modes (see Finding 7).

**Not present, and rightly not present per the brief:** no in-app username/password login, no per-user roles beyond the three access tiers, no in-app session management UI — consistent with "auth is a reverse-proxy concern" and not flagged as a gap.

## Positive / load-bearing

- Shutdown ordering in `internal/app/app.go` precisely matches the documented required order and is independently time-bounded per step (Findings 10-11).
- `ReloadDownloader`'s lock discipline and its interaction with `Shutdown`'s `stopWorkers` are both non-obviously correct and both explicitly documented in comments that name the specific race being closed (Findings 13-14).
- `go-standards.md` §4's "extract `mode`/`apikey` from query params first, form body second" rule is followed correctly and consistently (`apiKeyFromRequest`, `handleAPI`) — this is the exact rule the brief asked to specifically verify, and it holds.
- `TestQueueSlot_SonarrPercentageIsInt`/`TestQueueSlot_SonarrIndexField` show the team is already actively testing against the classic SABnzbd number-vs-string wire-format trap, not just hoping it doesn't bite (Finding 19).
- The `AppServices`/`JobManager`/`DownloaderControl`/`ConfigReloader`/`StatusReporter` role-interface split (`internal/api/roles.go` — note: this file, despite its name, is actually the role-interface definitions; `AccessLevel` itself lives in `middleware.go`) is a clean example of "define interfaces at the consumer side" (go-standards.md idiom #1) — handlers depend on narrow 1-9-method interfaces, not the full `*app.Application`, with a compile-time proof (`var _ JobManager = (*app.Application)(nil)`, etc.) that the split didn't silently drop a method.
- `redacted := s.config.Redacted()` before marshaling for `get_config` (`config.go:57-61`) — credential fields are actively scrubbed before ever reaching JSON encoding, not filtered after the fact. Good default-safe design.
- Config-set uses reflection with struct-tag lookup (`internal/config/set.go`) plus a rollback-on-validation-failure pattern (`prev := reflect.New(...); ...; field.Set(prev)` on error) — a defensible way to implement generic `set_config` without a hand-maintained giant switch statement, and it fails safe.
- `WebSocket` broadcaster (`events.go`) correctly follows the "never delete from a map while holding RLock" rule (go-standards.md §1): the overflow-handling path (lines 104-127) takes a full `Lock()` before deleting, after only `RLock()` was used for the broadcast-send loop. Ping/pong keepalive with a bounded write context (5s) and a bounded ping context (10s) means a dead TCP peer can't wedge a goroutine forever.
- `main.go`'s independent-context concurrent HTTP/HTTPS shutdown (`shutdownServeMode`, lines 357-390) has an unusually thorough comment explaining *why* a shared-context sequential approach would be wrong and that this was verified empirically rather than assumed — good practice matching the project's "verify, don't assume" standard.
