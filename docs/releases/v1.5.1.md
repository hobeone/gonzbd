## Upgrading from 1.5.0

No database schema, manifest format or configuration key changed.
An existing data directory from 1.5.0 works as it is.

This release contains a security fix; upgrade if gonzbd sits behind a reverse proxy.
A proxy that sends a forwarding header on several lines is now judged on every line,
so a request that was trusted on its first line alone can now be refused.

## Security

**A forwarding header sent on several lines is verified on every line.** (#1052)
The check that decides who receives the admin session cookie read `X-Forwarded-For`, `Forwarded` and `X-Real-IP` from their first line only.
A proxy that adds its own line rather than appending to the client's, such as HAProxy with `option forwardfor`, left the client's line first:
a client sending `X-Forwarded-For: 127.0.0.1` was verified on that line, and the proxy's line carrying its real address was never read.
An empty first line hid the header entirely, which also defeated the refusal that applies to a same-host proxy in the default configuration (`verify_xff_header: false`).
Every line of each header is now read as one list, as RFC 9110 specifies.
nginx's `$proxy_add_x_forwarded_for` appends to the client's line, so a setup using it was not affected.

## Highlights

**Stored RAR 1.5-4.x archives extract without `unrar`.**
With `use_go_rar` on (the default), the stored members of a RAR 1.5-4.x set (`.rar`, `.r00`, `.r01`, ...) now extract in-process, during DirectUnpack and after download.
A compressed or encrypted RAR 1.5-4.x member is still refused by the in-process reader; under `go_rar_fallback` it goes to `unrar` as before, and DirectUnpack leaves such a set to post-processing.

**The in-download archive peek reads RAR 1.5-4.x volumes.**
A completed RAR 1.5-4.x volume is now listed while the job downloads, as RAR5 volumes already were,
so a post whose volumes name an unwanted extension is paused or failed early, per `action_on_unwanted_extensions`,
rather than only having the file removed after unpack.
A RAR 1.5-4.x volume with encrypted headers cannot be listed and is still left to the post-unpack check.
